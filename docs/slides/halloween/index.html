A working example of using local AI on an iPhone. Qwen3-VL-2B on an iPhone 14 Pro, with no network connectivity.

AI Engineering meetup · Bill Mcintyre · October 22 2026

Happy almost-Halloween. Monster Scanner is a silly iPhone party game that scans a willing friend and reveals which monster they secretly are. It runs a 2-billion-parameter vision-language model fully on the phone. After one model download it never touches the network. Tonight: what the model does, how it runs, how we made a small model reliable and kind, and what it costs in speed and heat.

One: can a real language model run on an iPhone with no cloud? Two: what does it take: which runtime, which model size and quantisation fit in memory? The model narrates, the code decides. This is the one rule the whole design follows. Deterministic Swift measures the photo and picks the verdict. 05

Monster Scanner · Halloween edition

Every scan runs Classic measurements first, in under a second, using only Apple’s Vision models and pixel sampling. If the AI model is loaded and the phone isn’t hot, the observer reads a crop of the subject at the same time: Qwen3-VL-2B on llama.cpp, with a grammar that forces the JSON shape and a strict kindness check on all its text. Both lanes feed one deterministic verdict engine, seeded by a SHA-256 of the photo, with 47 clues on clothes, accessories, timing, pose and setting. The AI’s playful lines, the dashed green line, go straight to the reveal and are never scored. If the model is late, the phone is hot, or the JSON is invalid, the scan quietly uses Classic Mode.

One small open-weights vision-language model does all the AI work. Two GGUF files: the language model at 4-bit, Q4_K_M, and the vision projector at 8-bit, Q8_0. 07

Monster Scanner · Halloween edition

What the model does in the app. One: the observer runs on every scan. A crop of at most 512 pixels in, JSON out, with hair, eye and shirt colour, age band, expression, accessories and setting, plus three playful fields that are shown but never scored. Two: Chaos Mode, opt-in. The same call returns a 0 to 100 score per monster; code clamps them, the top one wins, and anything under 40 becomes certified human. Three: AI field notes, experimental and off by default. After the reveal it streams a short postscript, one checked sentence at a time, so it can never delay the reveal.

08

Monster Scanner · Halloween edition

The choice came down to provenance and support. It was the spec’s first choice, with official GGUF files from Qwen itself. The pinned llama.cpp build supports its architecture: the qwen3vl text model and the QWEN3VL projector. At 4-bit it fits next to the camera and UI on a 6 GB phone, and Apache 2.0 lets it ship in an app. A quick feasibility check in PocketPal came before any integration code. Qwen3.5-2B is the upgrade candidate, but it only has a community GGUF from Unsloth, which needs approval first. MLX, with mlx-swift-lm 3.32.3, stays the fallback runtime. The F16 projector, 819 MB, was kept in reserve in case Q8_0 hurt accuracy.

09

Monster Scanner · Halloween edition

The model runs on the A16’s GPU through llama.cpp’s official prebuilt xcframework, build b11799, MIT licensed. Its mtmd library handles image input. The catch: there is no Simulator slice, only iPhone and Mac, so llama.cpp links into device builds only and the Simulator plays Classic Mode. The Swift wrapper, LlamaEngine, is an actor on its own serial queue, so blocking C calls never touch the main thread. The lifecycle: verify the files, load in 0.73 seconds, unload on a memory warning or in the background, skip when hot. And a Mac twin, LlamaProbe, runs the same engine source at 126 tokens a second, so prompt experiments skip the phone.

10

Monster Scanner · Halloween edition

A GBNF grammar fixes the JSON shape at sampling time; the sampler decides what it costs. Without help, a 2B model wraps its JSON in code fences and invents accessories. A grammar over the full 152k vocabulary more than halves speed. Top-k first was fast but crashed once temperature was on, because it could pick a token the grammar forbids and llama.cpp throws a C++ exception. The shipped sampler draws one token freely, checks only that token, and resamples over the whole vocabulary only on a rare rejection. That is llama.cpp’s own approach. Result: valid JSON on every run, 5 of 5 on the phone, first try each time.

11

Monster Scanner · Halloween edition

Four more lessons. An early sampler copied every score into Swift for every token: 14 to 16 tokens a second on the phone instead of about 20, roughly a quarter of the speed gone. Greedy decoding, temperature 0, keeps readings reproducible; 0.6 was vaguer. Examples in a prompt get copied word for word: show a red bobble hat and it reports red bobble hats, so describe the style instead. And “only describe what you can clearly see; never invent items” stopped the invented hats and glasses. A parser that strips code fences, plus one retry, is the last line of defence; two failures means a silent fall back to Classic.

12

Monster Scanner · Halloween edition

The model never decides anything that is scored, except in opt-in Chaos Mode. Every piece of AI text passes three layers: prompt rules, grammar limits, and a kindness check in the model, with safety reinforced in code. Word lists cover unkind, age, looks and stereotype words, and a failing field is dropped on its own. Clothing colours like “black hat” stay fine; colour-plus-person phrases do not. Streamed field notes are held a sentence at a time and dropped if unkind, if they name another monster, or if they echo the instructions. In a 50-note test: 187 sentences kept, 13 dropped, none unkind. AI-written dossiers looped and copied their examples, so the comedy is code: 64 templates, exhibit jokes that slot in what the AI spotted, and the Bureau’s reasoning.

Monster Scanner · Halloween edition

Raw speed was fine on a cool phone. Heat was the real monster. Back-to-back scans on the charger took the phone to thermal “fair” at scan 6 and “serious” at scan 8, where generation runs at about half speed. Rather than tune a faster prompt, the app simply skips the model when hot, and scans 9 and 10 used Classic Mode with no crash. The worst shutter-to-reveal in the 10-scan soak was 9.1 seconds, against a 12-second budget. Other numbers: model load 0.73 seconds, about 20 tokens a second on the phone (105 to 126 on the Mac), 978 MB peak memory, and a 1.41-second SHA-256 check at launch.

15

Monster Scanner · Halloween edition

After a one-time 1.55 GB download, photos, model and results never leave the phone; it works in airplane mode. The only network code is the model download: HTTPS to the official Qwen org on Hugging Face, pinned to one repo commit, size shown first, Wi-Fi only by default. The runtime and both model files are pinned by SHA-256 and hashed again before the first load every launch, 1.41 seconds on the phone; a mismatch deletes the files and the app stays in Classic Mode. The build and repo were checked against GitHub, Hugging Face and the NIST CVE database first. One binary (llama.cpp, MIT) and one set of weights (Apache 2.0): no analytics, ads or accounts. Photos stay in memory, there is no face recognition, and shared images carry no metadata. New dependencies, network calls and permissions need the owner’s yes.

16

Monster Scanner · Halloween edition

Apart from llama.cpp, everything is Apple’s own on-device frameworks. Classic Mode uses no model of ours at all, only the models built into Vision: face rectangles and landmarks, plus Apple’s built-in image classifier, read through an allow-list of labels such as hats, sunglasses, beach or kitchen. Core Image adds smile and blink flags. Hair and shirt colour and blur are plain pixel sampling in Swift. ImageIO reads a photo’s capture time for the time-of-day clues, and ProcessInfo’s thermal state drives the heat fallback.

Monster Scanner · Halloween edition

An AI coding agent, Claude Code running Claude Opus 5.5, built the app from a written spec: the code, tests, scripts and docs. It built and deployed to the Simulator and the iPhone from the command line and ran the benchmarks. Helper agents in separate git worktrees built the sound effects, reveal effects and certificate in parallel. LlamaProbe is a Mac CLI on the same engine source, for prompt experiments. devicectl and scripts ran the benchmarks, a 10-scan soak and a 50-note kindness check; Swift Testing runs 76 tests covering verdict balance, kindness, the parser and determinism. The working agreement: plan, progress and decision logs updated together; small commits with human review at every milestone; ask before any dependency, network call or permission; flag spec problems rather than silently improvising.

18

Monster Scanner · Halloween edition

The biggest lesson: give a small local model the job it is good at, looking and describing, and keep judgement, jokes and safety in code. A grammar turned usually-JSON into always-valid JSON, but the sampler design decides whether that costs a few percent or more than half your speed. One Swift loop over the vocabulary cost about 25% of phone speed, so keep per-token work in C. Heat, not peak speed, is the phone’s real limit: plan the fallback. Small models copy examples word for word, so describe the style instead. A Mac twin of the engine turned every phone deploy into a one-second experiment. With a full non-AI mode, every failure is invisible to the player. Pin the commit, size and SHA-256 of every file and check before load. And a seeded, deterministic engine lets tests measure the verdict mix: a player found “everyone is a robot” twice, and now a balance test catches it first.
